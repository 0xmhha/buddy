# ADR-010 — v1.0.0 = whole-product completion, not plugin-only entry conditions

**Status**: Accepted (2026-05-19)
**Authors**: mhha (cli buddy + plugin track)
**Supersedes**: ADR-004 §2.2 *as the v1.0.0 trigger* (ADR-004's plugin version reset and namespace alignment stay valid; only its "B-1~B-4 = v1.0.0 trigger" framing is superseded here)
**Related**: ADR-005 (cli-buddy-spec lock-in), ADR-009 (cli buddy vision expansion), ADR-011 (release policy)

## Context

The F.3 alignment check on 2026-05-19 asked: *"v1.0.0 publish 가 plugin 만인지 binary 도 포함인지?"*

User's answer: **"계획한 모든 기능이 수행되는 상태가 v1.0.0 이다."**

ADR-004 §2.2 (plugin version reset, 2026-05-11) declared four conditions for the v1.0.0 entry point:

> B-1 cli buddy W3-2~W3-6 cascade 완료
> B-2 plugin+cli 통합 dogfood production-proven (외부 SaaS 1건 이상 end-to-end)
> B-3 PROCEDURE 양식 (B6) 통일 + `--strict` lint enforcement
> B-4 router smart-skip session state (B7) 해결 또는 supersede

By 2026-05-19, three of these were closed (B-1 / B-3 / B-4); B-2 was the lone remaining condition. The framing implied: "close B-2 → v1.0.0 publishes".

But ADR-009 (2026-05-19) expanded cli buddy's identity to include **five new responsibility areas** (F2.A Session Monitor / F2.B Usage Analysis / F2.C Advisory / F2.D Drift Detection / F2.E Notification — collectively "AI-usage coaching"). None of these are implemented. The user's stated v1.0.0 criterion — *"계획한 모든 기능이 수행되는 상태"* — necessarily includes the F2 areas too.

Therefore B-1~B-4 are *necessary but not sufficient* for v1.0.0. They are *plugin* v1.0.0 entry conditions, not *whole-product* v1.0.0.

## Decision

**v1.0.0 is the version stamped when *all planned features* are shipped end-to-end. "Planned" is defined by the sum of cli-buddy-spec §1.3 (post-ADR-009: 9 responsibilities) + plugin buddy charter scope (12 stages, all Done) + hook reliability monitor (M1~M6 + v0.1.0, Done).**

Concretely:

1. **Plugin entry conditions (ADR-004 §2.2, B-1~B-4) remain valid as *plugin-side* gates.** With B-3 / B-4 closed via ADR-006 / ADR-007 and B-1 closed via the v0.7.x bundle, only B-2 remains for the *plugin side*. Once B-2 closes, the *plugin* is v1.0.0-ready.
2. **cli buddy whole-product gates (NEW)**: cli buddy's nine responsibilities (per cli-buddy-spec §1.3, post-ADR-009) must all be shipped. The four agent-management responsibilities are done (v0.1 ~ v0.7.5). The five AI-usage coaching responsibilities (F2.A ~ F2.E) are 0% — they form a *separate* v1.0.0 gate, **named C-1 ~ C-5** below.
3. **whole-product v1.0.0 = (B-1 AND B-2 AND B-3 AND B-4 AND C-1 AND C-2 AND C-3 AND C-4 AND C-5) all closed.**

### C-1 ~ C-5 new entry conditions (cli buddy vision)

| Condition | Tied to | Definition |
|-----------|---------|-----------|
| **C-1** | F2.A Session Monitor (cli-buddy-spec §1.3 / W4) | A user's Claude Code sessions get tracked end-to-end. Activity ledger queryable via `buddy session ...` CLI + TUI pane. |
| **C-2** | F2.B Usage Analysis (W5) | Activity ledger → at least 3 analytic primitives (e.g., daily token spend / hook failure rate per skill / time-to-first-tool-call). MCP tools repurposed or added for AI-usage domain. |
| **C-3** | F2.C Advisory (W6) | At least one advisory rule fires real recommendations on real activity data ("이 hook 12% 실패 - X 권장" 같은 friend-tone Korean prose). |
| **C-4** | F2.D Drift Detection (W7) | A long conversation (>2h or >50 turns) with stated original goal can produce at least one drift alert when the topic shifts measurably. |
| **C-5** | F2.E Notification (W8) | At least one notification transport (TUI banner, OS notification, shell prompt status, or webhook) delivers advisories outside the user's active TUI session. |

### Hook reliability monitor

The v0.1.0 hook monitor pipeline is already Done (M1~M6 + release published 2026-04-26). No separate v1.0.0 entry condition needed; counted as part of the *whole product* baseline.

### Plugin buddy

The 9-phase orchestrator + 148 skills + 99 commands + 12 MCP tools are at 100% (per BACKLOG.md §2). Counted as baseline. The v1.0.0 plugin namespace decision happens *with the whole-product v1.0 bump*, not independently — i.e., plugin-only bumps via tag never reach `v1.0.0`; they remain on the v0.7.x patch line until *whole-product v1.0* is ready.

## Alternatives considered

### Option A — Plugin-only v1.0.0 (status quo before this ADR)

Once B-1 ~ B-4 all close, bump plugin marketplace.json to v1.0.0. cli buddy F2 vision stays on v0.x.

**Why rejected**:
- Conflicts with user's stated criterion ("계획한 모든 기능").
- Splits the version space across plugin and cli buddy — confusing for users who see a single `buddy` binary.
- Implies plugin "completion" while a large part of the stated vision (F2 areas) is unimplemented. Misleading semver semantics.

### Option B — Whole-product v1.0.0 with single combined entry-condition list (chosen)

The 9-condition list (B-1~B-4 + C-1~C-5) above.

**Why chosen**:
- Aligns with user's stated criterion.
- Single version namespace across both surfaces.
- C-1~C-5 are *explicit* and *testable* — the criteria for "F2 area is done" can be enforced via PR review + dogfood gate.

### Option C — Defer v1.0.0 indefinitely until "we feel like it"

No criterion at all.

**Why rejected**: vague triggers create indefinite drift. The B-X / C-X explicit list is more discipline-friendly even if total work is large.

## Consequences

- **`docs/HANDOFF.md` §1 Plugin v1.0.0 entry table** must change from 4 rows (B-1~B-4) to 9 rows (B-1~B-4 + C-1~C-5).
- **`BACKLOG.md` §2 진행률 표** must be re-computed against 9 conditions. With B-1/B-3/B-4 closed and B-2 ~5% + C-1~C-5 each 0%, the v1.0.0 progress drops from "75%" to roughly **33%** (3 of 9 conditions closed; B-2 partial doesn't substantially move it; C-1~C-5 all 0%). This is *real* progress, not a regression — the new total reflects the user's stated scope.
- **Plugin marketplace.json version** stays on v0.7.x until whole-product v1.0 ships. Plugin-only milestones (e.g., a new skill, a new MCP tool) bump *patch* or *minor* per ADR-011 (release-policy milestone-driven), but never reach 1.x without the C-1~C-5 conditions.
- **C-1~C-5 → W4~W8 phases** in cli-buddy-spec.md §9 already mirror this. The two are 1:1.
- **No code change today**: this ADR is governance. The next dogfood / impl cycle works against C-1~C-5 as fresh trigger conditions.

## Trigger to revisit

- If during F2 area design (per-area ADR), a condition turns out to be infeasible with current tech (e.g., F2.D requires LLM eval pass that's too expensive at scale), this ADR is amended to either drop the condition from v1.0 or postpone to v2.0.
- If user's vision evolves (post-dogfood), the C-X list itself can grow / shrink. Each change = a new ADR amending ADR-009 and this one in tandem.
