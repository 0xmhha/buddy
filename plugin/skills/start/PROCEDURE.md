# start — 사용자 의도 기반 진입 라우터

사용자가 자연어로 의도를 표현하면 적절한 작업 흐름으로 라우팅한다. 사용자에게는 자연스러운 질문만 보여주고, 내부의 Mode A/B 같은 분류 용어는 노출하지 않는다.

**진입 조건**: 어떤 command를 써야 할지 모를 때 / 새 작업의 시작점 / 처음 buddy 사용 시.
**산출물**: 사용자 컨텍스트 수집 + 적절한 orchestrator로의 dispatch.
**다음 phase**: 라우팅된 orchestrator의 흐름을 따름.

## Input Requirements

| Input | Required | Type | Source | 미제공 시 |
|-------|----------|------|--------|----------|
| 사용자 의도 (자연어 발화) | 선택 | knowledge | `$ARGUMENTS` | 질문으로 단계별 수집 |

## Output Contract

| Output | Type | Format | Consumers |
|--------|------|--------|-----------|
| 수집된 사용자 컨텍스트 (프로젝트 경로, 작업 유형, 상업성) | knowledge | inline + 다음 스킬에 전달 | `concretize-idea`, `assess-product-change` |
| Dispatch decision | decision | Skill tool 호출 | 결정된 target orchestrator |

---

## 수집 정보 (사용자에게 묻거나 발화에서 추출)

| 항목 | 가능한 값 | 영향 |
|------|---------|------|
| 기존 프로젝트 경로 | 경로 문자열 / 없음 | 작업 흐름의 시작점 결정 |
| 작업 유형 | 신규 기능 / 버그 수정 / 개선 / 리팩토링 / 신규 아이디어 구체화 / 기타 | 라우팅 + 후속 단계 |
| 상업성 | 상업용 / 비상업(학습/해커톤/OSS/hobby) / 아직 모름 | 사업성 검증 단계 포함 여부 |

---

## 실행 절차

### Step 1. 입력 확인

`$ARGUMENTS` 검사:
- 비어있음 → Step 2로 (질문 시작)
- 내용 있음 → Step 2.1로 (발화에서 정보 추출 후 누락된 것만 질문)

### Step 2.1. 발화에서 정보 추출 (입력 있을 때)

발화에서 다음 단서를 추출:

| 단서 | 추출 정보 |
|------|---------|
| "이 프로젝트", "내 코드", 파일/디렉토리 경로 언급 | 기존 프로젝트 있음 (경로 확인 질문은 그래도 필요) |
| "버그", "안 돌아가", "고쳐" | 작업 유형 = 버그 수정 |
| "기능 추가", "feature" | 작업 유형 = 신규 기능 |
| "리팩토링", "개선", "최적화" | 작업 유형 = 개선/리팩토링 |
| "아이디어가 있어", "새로 만들고 싶어" | 신규 아이디어 구체화 |
| "스타트업", "사업", "수익" | 상업성 = 상업용 |
| "학습", "공부", "해커톤", "OSS", "hobby" | 상업성 = 비상업 |

추출된 정보를 기반으로 **누락된 항목만** 질문한다 (이미 명확하면 다시 묻지 않음).

### Step 2.2. 프로젝트 경로 확인 (없을 때 기본 시작점)

> "기존에 작업하시던 프로젝트가 있나요? 있다면 경로를 알려주세요.
> (없으면 '없음' 또는 빈 답변 OK)"

**응답 처리**:
- 경로 제공 → 경로 존재 여부 확인 후 진행
- "없음" / 빈 답변 → 신규 작업으로 진행

### Step 2.3. 작업 유형 질문

**기존 프로젝트가 있는 경우**:
> "어떤 작업을 하시려고 하나요?
> a) 신규 기능 추가
> b) 버그 수정
> c) 개선 / 리팩토링 / 성능 최적화
> d) 의존성 갱신
> e) 기타 (자유 설명)"

**기존 프로젝트가 없는 경우**:
> "어떤 아이디어를 구체화하시나요? 한 문장으로 설명해 주세요."

### Step 2.4. 상업성 질문

> "이 작업이 상업용 프로젝트인가요?
> - **상업용**: 사업성 평가 + pricing/GTM 검토 단계가 포함됩니다.
> - **비상업** (학습 / 해커톤 / 개인 hobby / OSS): 사업성 단계는 생략하고 빠르게 진행합니다.
> - **아직 모름**: 일단 비상업으로 진행하고, 후에 상업화 결정 시 별도 단계 추가 가능.
>
> (상업용 / 비상업 / 아직 모름)"

### Step 3. 수집 정보 확인

```
다음과 같이 진행할게요:
  ● 작업: <기존 프로젝트 변경 | 신규 아이디어 구체화>
  ● 프로젝트 경로: <경로 / 해당 없음>
  ● 작업 유형: <기능 추가 / 버그 수정 / ...>
  ● 상업성: <상업용 / 비상업 / 아직 모름>

맞나요? (y / 수정할 부분 알려주세요)
```

사용자가 'y' 또는 동의 응답 시 Step 4로. 수정 요청 시 해당 항목 다시 질문.

### Step 4. 라우팅

수집된 정보로 target orchestrator 결정:

| 조건 | 라우팅 대상 | 전달 컨텍스트 |
|------|-----------|------------|
| 기존 프로젝트 + 모든 작업 유형 | `assess-product-change` | 경로, 작업 유형, 상업성 |
| 신규 아이디어 | `concretize-idea` | 아이디어 설명, 상업성 |
| 위 두 가지가 모두 아닌 모호한 경우 | 다시 Step 2로 (질문 정정) | — |

`Skill` tool로 dispatch. 수집한 컨텍스트를 인자로 전달해서 orchestrator가 같은 질문을 반복하지 않도록 한다.

---

## 이 스킬을 사용하는 경우

- 처음 buddy를 사용해서 어떤 command가 있는지 모름
- 자기 의도를 자연어로 표현하고 싶음
- "어디서부터 시작할지 모르겠음"
- 시연 / 데모 / onboarding 시점

## 이 스킬을 사용하지 않는 경우

- 진행 중인 작업 이어가기 → `/buddy:restore-context`
- 현재 phase 확인만 필요 → `/buddy:status`
- (참고) Mode A/B orchestrator(`concretize-idea`, `assess-product-change`)는 슬래시 직접 호출이 없음 — `/buddy:start`가 라우팅
- 현재 phase가 궁금함 → `/buddy:status`
