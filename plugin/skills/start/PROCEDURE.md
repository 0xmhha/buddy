# start — 사용자 의도 기반 진입 라우터

사용자가 자연어로 의도를 표현하면 적절한 작업 흐름으로 라우팅한다. 사용자에게는 자연스러운 질문만 보여주고, 내부의 Mode A/B 같은 분류 용어는 노출하지 않는다.

**진입 조건**: 어떤 command를 써야 할지 모를 때 / 새 작업의 시작점 / 처음 buddy 사용 시.
**산출물**: 사용자 컨텍스트 수집 + 적절한 orchestrator로의 dispatch.
**다음 phase**: 라우팅된 orchestrator의 흐름을 따름.

## Input Requirements

| Input | Required | Type | Source | 미제공 시 |
|-------|----------|------|--------|----------|
| 사용자 의도 (자연어 발화) | 선택 | knowledge | `$ARGUMENTS` | 질문으로 단계별 수집 |

## Output Contract

| Output | Type | Format | Consumers |
|--------|------|--------|-----------|
| 수집된 사용자 컨텍스트 (프로젝트 경로, 작업 유형, 상업성) | knowledge | inline + 다음 스킬에 전달 | `concretize-idea`, `assess-product-change` |
| Dispatch decision | decision | Skill tool 호출 | 결정된 target orchestrator |

---

## 수집 정보 (사용자에게 묻거나 발화에서 추출)

| 항목 | 가능한 값 | 영향 |
|------|---------|------|
| 기존 프로젝트 경로 | 경로 문자열 / 없음 | 작업 흐름의 시작점 결정 |
| 작업 유형 | 신규 기능 / 버그 수정 / 개선 / 리팩토링 / 신규 아이디어 구체화 / 기타 | 라우팅 + 후속 단계 |
| 상업성 | 상업용 / 비상업(학습/해커톤/OSS/hobby) / 아직 모름 | 사업성 검증 단계 포함 여부 |

---

## 실행 절차

### Step 1. 입력 확인

`$ARGUMENTS` 검사:
- 비어있음 → Step 2로 (질문 시작)
- 내용 있음 → Step 2.1로 (발화에서 정보 추출 후 누락된 것만 질문)

### Step 2.1. 발화에서 정보 추출 (입력 있을 때)

발화에서 다음 단서를 추출:

| 단서 | 추출 정보 |
|------|---------|
| "이 프로젝트", "내 코드", 파일/디렉토리 경로 언급 | 기존 프로젝트 있음 (경로 확인 질문은 그래도 필요) |
| "버그", "안 돌아가", "고쳐" | 작업 유형 = 버그 수정 |
| "기능 추가", "feature" | 작업 유형 = 신규 기능 |
| "리팩토링", "개선", "최적화" | 작업 유형 = 개선/리팩토링 |
| "아이디어가 있어", "새로 만들고 싶어" | 신규 아이디어 구체화 |
| "스타트업", "사업", "수익" | 상업성 = 상업용 |
| "학습", "공부", "해커톤", "OSS", "hobby" | 상업성 = 비상업 |

**단서 충돌 시 우선순위 (R4 — 라우팅 결정성 보장)**:

| 우선순위 | 규칙 | 예시 / 처리 |
|---------|------|----------|
| 1 (최강) | **명시적 경로** (`./`, `/`, `~/`, `.\`, `C:\` 등 path-like 문자열) | "./my-project에서 버그 고쳐줘" → 경로 = `./my-project`, "이 프로젝트" 같은 모호 표현보다 우선 |
| 2 | **모순 단서 충돌** (기존 프로젝트 시그널 + 신규 아이디어 시그널 동시) — 자동 추정 금지 | "이 프로젝트에 새 기능 추가하고 싶은데 새로 만들고 싶어" → 자동 추정 X → Step 2.2 직접 질의로 직행 ("기존 프로젝트의 새 기능인가요, 별도 신규 프로젝트인가요?") |
| 3 | **작업 유형 단서 > 상업성 단서** | "스타트업 버그 수정해줘" → 작업 유형(버그 수정)이 라우팅 결정, 상업성은 부가 정보 |
| 4 (최약) | **모호 표현만** ("이거", "그거" 등 지시어만) | 단서 추출 실패로 처리 → 누락 질문으로 폴백 |

추출된 정보를 기반으로 **누락된 항목만** 질문한다 (이미 명확하면 다시 묻지 않음). 단서 충돌이 감지되면 추정하지 말고 Step 2.2-2.4 직접 질의로 우회한다.

### Step 2.2. 프로젝트 경로 확인 (없을 때 기본 시작점)

> "기존에 작업하시던 프로젝트가 있나요? 있다면 경로를 알려주세요.
> (없으면 '없음' 또는 빈 답변 OK)"

**응답 처리** (R2 — 경로 검증 실패 동작 명시):

1. **경로 제공**: 다음 검증 실행:
   ```
   !`test -d "<received-path>" && echo "EXISTS" || echo "MISSING"`
   ```
   결과에 따라 분기:
   - `EXISTS` → 기존 프로젝트로 확정. Step 2.3으로 진행
   - `MISSING` → 사용자에게 재질의: "경로 `<path>`가 존재하지 않습니다. 다시 확인해 주세요. (정확한 경로 또는 '없음'으로 답변)"
     - 재질의 후 다시 경로 제공 → 재검증
     - 재질의 후 '없음' → 신규 작업으로 진행
     - 재질의 3회 연속 실패 → 사용자에게 보고 후 작업 중단 (router의 무한 루프 방지)
2. **"없음" / 빈 답변** → 신규 작업으로 진행 (Step 2.3 신규 분기로)
3. **답변 모호** ("있을 수도", "잘 모르겠어" 등) → 한 번 더 명확화 질의: "있음/없음 중 하나로 답변해 주세요". 2회 실패 시 '없음'으로 처리하고 신규 작업으로 진행

### Step 2.3. 작업 유형 질문

**기존 프로젝트가 있는 경우**:
> "어떤 작업을 하시려고 하나요?
> a) 신규 기능 추가
> b) 버그 수정
> c) 개선 / 리팩토링 / 성능 최적화
> d) 의존성 갱신
> e) 기타 (자유 설명)"

**기존 프로젝트가 없는 경우**:
> "어떤 아이디어를 구체화하시나요? 한 문장으로 설명해 주세요."

### Step 2.4. 상업성 질문

> "이 작업이 상업용 프로젝트인가요?
> - **상업용**: 사업성 평가 + pricing/GTM 검토 단계가 포함됩니다.
> - **비상업** (학습 / 해커톤 / 개인 hobby / OSS): 사업성 단계는 생략하고 빠르게 진행합니다.
> - **아직 모름**: 일단 비상업으로 진행하고, 후에 상업화 결정 시 별도 단계 추가 가능.
>
> (상업용 / 비상업 / 아직 모름)"

### Step 3. 수집 정보 확인

```
다음과 같이 진행할게요:
  ● 작업: <기존 프로젝트 변경 | 신규 아이디어 구체화>
  ● 프로젝트 경로: <경로 / 해당 없음>
  ● 작업 유형: <기능 추가 / 버그 수정 / ...>
  ● 상업성: <상업용 / 비상업 / 아직 모름>

맞나요? (y / 수정할 부분 알려주세요)
```

**응답 처리** (R5 — 수정 항목 추출 규칙):

| 사용자 응답 | 처리 |
|----------|------|
| `y`, `yes`, `네`, `맞아`, `진행`, `ok` 등 동의 표현 | Step 4로 진행 |
| 명시적 항목 언급: "경로 수정", "작업 유형 다시", "상업성 변경" 등 | 해당 Step만 재질문 (경로 → 2.2, 작업 유형 → 2.3, 상업성 → 2.4) |
| 모호 응답: "n", "아니야", "수정" (어떤 항목인지 불명) | 직접 질의: "어느 항목을 수정할까요? (1) 경로 (2) 작업 유형 (3) 상업성 (4) 전체 다시" |
| "전체 다시", "처음부터" | Step 2.1부터 재시작 |
| 무관한 응답 (e.g. 새 질문) | 한 번 더 확인: "확정(y) / 수정(어느 항목?) 중 답변해 주세요". 2회 실패 시 'y'로 간주하고 진행 |

수정 후 자동으로 Step 3 (수집 정보 확인)으로 돌아와 다시 확인. 무한 수정 루프 방지를 위해 같은 항목 5회 연속 수정 시 사용자에게 보고 후 작업 중단.

### Step 4. 라우팅

수집된 정보로 target orchestrator 결정. **단일 분기 기준은 "경로 유무"** (가이드 §1.4 Mode 결정 원칙).

**라우팅 결정 매트릭스** (R1 — 모든 입력 조합에 대해 정책 명시):

| # | 조건 | 라우팅 대상 | 전달 컨텍스트 |
|---|------|-----------|------------|
| 1 | **경로 검증 통과** (Step 2.2 EXISTS) + 작업 유형(a-e) 명시 | `assess-product-change` (Mode B) | 경로, 작업 유형, 상업성 |
| 2 | **경로 없음/'없음'** + 아이디어 설명 1 문장 이상 | `concretize-idea` (Mode A) | 아이디어 설명, 상업성 |
| 3 | **모순 입력**: 경로 검증 통과 + 동시에 "신규 아이디어 설명"이 추출됨 | Step 2.2로 회귀, 사용자 직접 질의: "기존 프로젝트의 새 기능인가요(Mode B), 별도 신규 프로젝트인가요(Mode A)?" — 사용자 선택 후 해당 라우팅 적용 | — |
| 4 | **누락 입력**: 경로 답변만 있고 작업 유형 무답변 | Step 2.3으로 회귀하여 작업 유형 재질의 | — |
| 5 | **누락 입력**: 경로 없음이고 아이디어 설명도 없음/한 단어 | Step 2.3 신규 분기로 회귀하여 "어떤 아이디어를 구체화하시나요? 한 문장으로 설명해 주세요" 재질의 | — |

**"모호" 정의** (R3 — Step 2 회귀 trigger 조건 명시):

다음 중 **하나라도** 해당하면 위 매트릭스의 #3-#5 중 적합한 행으로 처리. 그래도 분류 불가하면 Step 2.1부터 재시작:

- 경로 답변이 yes/no 불명 (Step 2.2 모호 응답이 2회 명확화 실패)
- 작업 유형 답변이 a-e 외 또는 무응답
- 아이디어 설명이 1단어 미만 (지시어 "이거", "그거" 등만)
- Step 2.1 발화 단서 충돌이 감지되었으나 Step 2.2 직접 질의로도 해소 안 됨

**Dispatch 실행**:

`Skill` tool로 dispatch. 수집한 컨텍스트를 인자로 전달해서 orchestrator가 같은 질문을 반복하지 않도록 한다. 전달 컨텍스트 구조:

```yaml
# Mode B 진입 시
target_orchestrator: assess-product-change
context:
  project_path: "<verified-path>"
  change_type: "feature" | "bugfix" | "refactor" | "dependency-update" | "other"
  commercial: "commercial" | "non-commercial" | "unknown"

# Mode A 진입 시
target_orchestrator: concretize-idea
context:
  idea_description: "<1+ sentence>"
  commercial: "commercial" | "non-commercial" | "unknown"
```

라우팅 후 본 skill 종료. orchestrator의 흐름이 이어 시작된다.

## 이 스킬을 사용하는 경우

- 처음 buddy를 사용해서 어떤 command가 있는지 모름
- 자기 의도를 자연어로 표현하고 싶음
- "어디서부터 시작할지 모르겠음"
- 시연 / 데모 / onboarding 시점

## 이 스킬을 사용하지 않는 경우

- 진행 중인 작업 이어가기 → `/buddy:restore-context`
- 현재 phase 확인만 필요 → `/buddy:status`
- (참고) Mode A/B orchestrator(`concretize-idea`, `assess-product-change`)는 슬래시 직접 호출이 없음 — `/buddy:start`가 라우팅
- 현재 phase가 궁금함 → `/buddy:status`

## 출력 형식

본 skill의 산출물은 두 가지:

1. **사용자 컨텍스트 수집 결과** (Step 3에서 사용자 확인용 inline 표시): 4 항목 — 작업 / 프로젝트 경로 / 작업 유형 / 상업성
2. **Dispatch context** (Step 4에서 target orchestrator에 전달): YAML schema는 **Step 4 "Dispatch 실행" 블록 참조** — Mode A(`concretize-idea`)와 Mode B(`assess-product-change`)가 각각 다른 schema를 받음

본 skill 자체는 별도 리포트를 출력하지 않음. dispatch 직후 종료되고 orchestrator의 흐름이 사용자에게 보이는 산출물을 책임진다.

## 검증 체크리스트 (Step 4 dispatch 직전)

다음 7항목을 모두 충족해야 dispatch 진행:

- [ ] 사용자에게 Mode A/B 같은 내부 용어를 노출하지 않았음 (자연어 질문만 사용)
- [ ] 경로 검증 결과 EXISTS 또는 명시적 '없음' 응답 확보 (Step 2.2)
- [ ] Mode B 진입 시: 작업 유형 a-e 중 하나 확정 또는 '기타' 자유 설명 확보 (Step 2.3)
- [ ] Mode A 진입 시: 아이디어 설명 1문장 이상 확보 (Step 2.3 신규 분기)
- [ ] 상업성 3종(상업/비상업/모름) 중 하나 확정 (Step 2.4)
- [ ] Step 3 수집 정보 확인에서 사용자 동의(`y` 또는 동등 표현) 획득
- [ ] Step 4 라우팅 매트릭스 5행 중 하나로 명확히 분류됨 (#3-#5 회귀 처리 케이스는 dispatch 안 함)

7개 중 하나라도 미충족 시 dispatch 금지 — 해당 Step으로 회귀.

## Anti-patterns (R1-R5 정책 영속 강제)

| ❌ Bad | ✅ Good | 이유 |
|--------|--------|------|
| 사용자에게 "Mode A로 라우팅합니다" / "이 입력은 Mode B 케이스입니다" 노출 | "기존 프로젝트가 있나요?" / "어떤 작업이세요?" — 자연어 질문만 | 내부 분류 용어는 UX 오염. start의 정체성에 명시된 원칙 |
| 경로 답변을 받자마자 검증 없이 Step 2.3 진행 | `` !`test -d "<path>"` `` 검증 후 EXISTS만 진행, MISSING 시 재질의 | R2 — 잘못된 경로로 Mode B 진입 시 후속 orchestrator 실패 |
| 단서 충돌 시 LLM 추정으로 Mode 결정 ("이 프로젝트에 새로 만들고 싶어" → 임의로 Mode A 또는 B) | 자동 추정 금지. Step 2.2 직접 질의로 우회 | R4 — 라우팅 결정성 보장. 추정은 비결정적 결과 유발 |
| Step 4 라우팅 매트릭스 5행 외 케이스를 LLM이 즉흥 처리 | 5행 중 하나로 분류 불가하면 Step 2.1 재시작 | R1+R3 — 명시되지 않은 분기 처리는 비결정적 |
| Step 3 "수정" 응답에 어떤 항목인지 묻지 않고 전체 다시 진행 | 항목 명시 추출 또는 "어느 항목?" 직접 질의 | R5 — 불필요한 전체 재진입 방지 (사용자 시간 낭비) |
| dispatch 시 context 누락 (`Skill` tool에 인자 없이 호출) | Step 4 YAML schema대로 모든 필드 전달 | orchestrator가 같은 질문 반복 → UX 깨짐 |
| 무한 재질의 (경로/수정 응답이 계속 모호해도 계속 묻기) | 경로 3회, 수정 5회 한계 도달 시 사용자 보고 후 중단 | router 무한 루프 방지 |
| Mode A/B orchestrator를 사용자가 직접 호출하도록 안내 | "/buddy:start로 시작하세요" 안내 | command 부재로 직접 호출 차단 (가이드 §1.2.3 buddy 등가 매핑) |
